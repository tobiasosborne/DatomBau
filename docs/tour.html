The database that remembers everything

An interactive tour of DatomBau — a small Datomic-style database rebuilt in the Lean 4 theorem prover, where the promises come with machine-checked proofs.

Most databases store a system's current state and destroy the past on every update — like knowing a particle's position now, with no record of its trajectory. DatomBau (like Datomic, the database it reimplements) stores the whole trajectory: an append-only log of events. The current state, states at any earlier time, indexes, and query answers are all just projections of that log. And because it lives inside a proof assistant, "just projections" is not a slogan — it is a list of theorems.

A datom is the atomic unit: one timestamped, signed statement about the world. Click the slots.

Everything in the database is built from these five-part events. Nothing is ever overwritten: to change Ada's name you don't edit a row, you append a retraction of the old fact and an assertion of the new one — both stamped with the transaction in which they happened.

The rule for "is fact f true at basis t?" is one line: find the last datom about f with transaction ≤ t; the fact holds iff that datom was an assertion. In DatomBau this really is the definition — a function called lastWrite — and time travel (asOf t) is nothing more than filtering the log to transactions ≤ t. Try appending a transaction while the slider sits in the past: the view at t cannot move, and that's a theorem, not an observation.

-- Spec.lean — value equality, no side conditions beyond freshness: theorem Db.asOf_append (hfresh : db.maxTx < t.id) (htx : tx ≤ db.maxTx) : (db.append t).asOf tx = db.asOf tx

Fig. 3 — Four coordinate systems, one reality

Indexes · the same current facts, sorted four ways

An index is a choice of coordinates on the same set of events — sorting by entity-first makes "everything about #2" a contiguous block; value-first makes "who points at #1" contiguous instead. No new information is created by re-sorting, and DatomBau proves precisely that: membership in each index is equivalent to the log's lastWrite saying "asserted, in exactly that transaction". The coordinate change provably preserves the physics.

A query is a conjunction of patterns; variables (?g, ?f, ?n) thread through them and each clause filters-and-extends the set of consistent assignments. DatomBau's engine is deliberately the dumbest possible left-to-right fold — because that shape is what makes the two flagship proofs go through: soundness (every answer really matches every clause) and completeness (every assignment that matches is found). Fast evaluation via the indexes is then proven equivalent through a single bridge theorem, so optimization can never silently change an answer.

What "verified" buys you

Ordinary databases test their promises; DatomBau proves them. Each layer of the system earns a flagship theorem, checked by Lean's kernel — there is no sorry (unproven claim) anywhere on the main branch:

asOf_appendAppending never changes any past view — as literal equality of database values.
transact_wfThe transactor preserves well-formedness: monotone time, bounded ids, every stored datom well-typed.
transactAt_cardOneA cardinality-one attribute never holds two values at once.
transactAt_uniqueA unique (attribute, value) pair identifies at most one entity.
ofDb_wfIndex membership ⇔ the log's last write asserted the fact, in exactly that transaction.
evalSpec_sound / _completeQuery answers are exactly the matching assignments — nothing bogus, nothing missed.
evalIdx_mem_iffThe index-backed engine answers exactly what the reference engine answers.
query_asOf_stableNo future transaction can change the answer of any query about the past.
DatomBau is ~2,400 lines of Lean 4 with zero external dependencies — source, theorems, and demo at github.com/tobiasosborne/DatomBau. The written tutorial (TUTORIAL.md) walks through the same ideas with runnable code, and ./run.sh executes the end-to-end demo this page is based on.
